\section{Pendahuluan}

Permintaan \textit{Application Programming Interface} (API) baru datang dari vendor, perusahaan asuransi, dan unit rumah
sakit secara bersamaan. Anggaran tidak cukup untuk semuanya. Tonggak C2 sudah memperlihatkan keadaan saat ini. Sepuluh
baris inventaris mewakili 100 sambungan. Sebanyak 20 sambungan aktif dari Sistem Informasi Manajemen Rumah Sakit (SIMRS)
menelan Rp900 juta per tahun pada Rp45 juta per antarmuka. Kerja manual lima baris lain berjumlah 357 jam per bulan, atau
Rp257,04 juta per tahun pada tarif Rp60.000 per jam. Medikara belum punya satu pun API mitra. Misalkan direksi hanya
menyediakan anggaran untuk tiga API tahun depan, sedangkan daftar permintaan berisi delapan. Pertanyaan kemudian muncul:
API mana yang dikerjakan lebih dahulu, dan siapa yang berhak memutuskannya?

Bab ini menjawabnya dengan menurunkan portofolio API dari tujuan dan perjalanan pengguna, sehingga urutan pekerjaan tidak
ditentukan oleh pihak yang paling keras meminta. Bab ini membuka tonggak C3 Kondisi Target. Inventaris Bab 4, peta
integrasi Bab 5, penilaian keamanan Bab 6, dan penilaian kesiapan Bab 7 menjadi masukan. \textit{Capability map} dan
\textit{value stream} diambil dari IT40513 Enterprise Architecture \& Digital Blueprint. Kontrak API dibahas di Bab 9,
\textit{API gateway} di Bab 10, portal pengembang di Bab 11, dan monetisasi di Bab 12, sehingga di sini cukup dirujuk.
Angka tambahan yang diawali kata ``Misalkan'' adalah asumsi latihan. Kesimpulan untuk organisasi nyata harus diuji dengan
wawancara, dokumen, dan pengukuran yang berizin. Hasil bab ini menjadi bagian C3 dalam cetak biru transformasi digital.

Rujukan utama bab ini dipakai untuk membedakan konsep dan membangun alasan keputusan, bukan untuk menggantikan penilaian

\section{Dari Strategi Platform ke Strategi API}

Bab 2 dan Bab 3 sudah menetapkan arah platform Medikara. Janji temu menjadi interaksi inti, klinik mitra membayar
langganan, dan asuransi membayar verifikasi penjaminan. Arah itu belum menjawab pertanyaan yang diajukan vendor setiap
minggu: kemampuan mana yang dibuka lewat API?

Strategi API menerjemahkan tujuan platform menjadi kemampuan yang dapat dikonsumsi pihak tertentu. Tujuan menyebut hasil
organisasi, pengguna yang dilayani, dan perubahan perilakunya. Jumlah API bukan strategi. Kandidat harus mempunyai hubungan
yang dapat ditelusuri ke masalah serta ukuran hasil, termasuk keputusan untuk tidak membuka suatu kemampuan. Parker dkk.
menempatkan interaksi inti sebagai pusat rancangan platform \cite{parker2016platform}, sehingga API yang tidak
memperlancar interaksi itu memerlukan alasan lain, misalnya kewajiban atau penghematan.

Analoginya daftar menu. Daftar menu mengikuti kebutuhan pelanggan dan kemampuan dapur, bukan daftar seluruh bahan yang
tersedia. Dapur yang menyimpan lima puluh bahan tidak otomatis menawarkan lima puluh hidangan, dan sebagian bahan memang
tidak pernah dijual mentah.

Dua contoh berangka pada Medikara:
\begin{enumerate}
  \item Tujuan mempercepat pemesanan dari klinik mitra melahirkan tiga kemampuan: pencarian layanan, verifikasi syarat, dan
        pemesanan. Ketiganya dinilai sebagai satu perjalanan. Bab 3 menghitung satu klinik melayani 60 kunjungan per hari,
        dan satu pemesanan butuh tiga panggilan, atau 180 panggilan per klinik. Untuk 40 klinik mitra, kebutuhannya 7.200
        panggilan per hari, atau 60 persen dari kapasitas 12.000 panggilan pada kuota 300 per hari per klinik. Ukuran
        keberhasilannya adalah janji terkonfirmasi, bukan jumlah \textit{endpoint}.
  \item Misalkan vendor analitik mengusulkan API untuk mengunduh seluruh data pasien, atau sekitar 1,2 juta kunjungan per
        tahun. Usulan ini ditolak bila tidak ada tujuan sah dan kebutuhan pengguna yang teruji. Insiden 2025 pada Bab 6
        melibatkan 1.240 rekam, atau sekitar 0,1 persen dari jumlah itu, dan biaya langsungnya pada pemisalan Bab 6 sudah
        Rp23,7 juta. Keputusan tidak membuka sebuah kemampuan juga bagian dari strategi, sehingga dicatat beserta
        alasannya.
\end{enumerate}

Apakah bukti empiris mendukung pembukaan API seluas mungkin? Tiga sumber perlu dibaca bersama. Benzell dkk. menemukan
perusahaan terbuka yang mengadopsi API publik tumbuh tambahan 38,7 persen selama 16 tahun dibanding perusahaan serupa.
Pemakaian API untuk produktivitas internal saja tidak menunjukkan efek signifikan, dan risiko kebocoran data ikut naik
\cite{benzell2024apis}. Wulf dan Blohm mensurvei 152 manajer produk API. Mereka menemukan bahwa strategi penciptaan nilai
memoderasi hubungan antara rancangan API dan dua hasil, yaitu laba atas investasi dan penyebaran \cite{c08-wulf2020}.
Laporan Postman mencatat 65 persen organisasi memperoleh pendapatan dari program API, sementara 34 persen tidak dapat
menemukan API yang sudah ada \cite{postman2025}.

Ketiganya tidak berarti Medikara harus membuka API publik. Benzell dkk. meneliti perusahaan tercatat di bursa, Wulf dan
Blohm meneliti API publik, dan Postman menjual alat API. Yang dapat diambil lebih sempit: rancangan API perlu selaras dengan
tujuan bisnis, dan jumlah API tanpa keterlihatan dapat menjadi beban. Zimmermann dkk. membedakan API menurut
keterlihatannya, yaitu \textit{public API}, \textit{community API}, dan \textit{solution-internal API}
\cite{zimmermann2022patterns}. Pembagian ini sejajar dengan audiens publik, mitra, dan privat pada Bab 4. Portofolio
Medikara terutama berisi API mitra dan API privat, karena data pasien tidak cocok dibuka kepada pihak yang tidak dikenal.

Keputusan menurunkan API dari tujuan punya dua konsekuensi. Pertama, permintaan yang tidak terhubung ke tujuan ditolak

Dua hal pada bahasan ini sering tertukar, yaitu strategi platform dan strategi API. Pembagiannya begini. Strategi platform
menjawab siapa bertemu siapa, nilai apa yang dipertukarkan, dan siapa membayar. Strategi API menjawab kemampuan mana

misalnya API privat yang hanya menyederhanakan 20 sambungan internal.

\section{Menurunkan Kandidat API dari Kapabilitas Bisnis}

Cara paling cepat menyusun daftar API adalah membuka daftar sistem, lalu membuat API untuk tiap sistem. Hasilnya mengikuti
bentuk SIMRS hari ini. Apa alternatifnya?

\textit{Capability map} menjelaskan kemampuan bisnis, sedangkan \textit{value stream} menjelaskan rangkaian nilai dari
sudut pengguna. Kapabilitas menyatakan kemampuan yang dimiliki organisasi untuk mencapai tujuan tertentu, terlepas dari
unit atau aplikasi yang menjalankannya \cite{c08-togaf-g211}. \textit{Value stream} adalah rangkaian tahap ujung ke ujung
yang menghasilkan nilai bagi penerima tertentu \cite{c08-togaf-g178}. Keduanya terhubung, karena kapabilitas memungkinkan
tahap dalam \textit{value stream} berjalan \cite{c08-bizbok15}. Kandidat API muncul pada titik ketika kemampuan perlu
dipakai lintas batas. Daftar sistem hanya menunjukkan lokasi implementasi sekarang. Kandidat berbasis kemampuan lebih tahan
terhadap perubahan vendor, tetapi tetap memerlukan penilaian kelayakan sistem lama.

Analoginya papan nama loket. Nama loket mengikuti layanan yang diberikan, bukan merek komputer yang dipakai petugas. Pasien
mencari loket pendaftaran. Ketika komputernya diganti, papan namanya tetap.

Dua contoh berangka pada Medikara:
\begin{enumerate}
  \item Kapabilitas Penjadwalan Layanan (CAP-L03) dapat dilayani melalui satu API janji temu meskipun lima SIMRS mempunyai
        struktur berbeda. Bila API diturunkan dari daftar sistem, ada 5 API jadwal, dan 40 klinik mitra masing-masing
        menyambung ke kelimanya, atau 200 sambungan di sisi klinik. Bila diturunkan dari kapabilitas, ada 40 sambungan.
        Penyedia justru membayar lebih. Lima API berbiaya Rp225 juta per tahun, sedangkan 1 API ditambah 5 adaptor berbiaya
        Rp270 juta per tahun. Selisih Rp45 juta itu adalah harga untuk melindungi klinik dari perubahan. Bab 4 memisalkan
        satu perubahan menyita 4 jam per klinik, atau 160 jam untuk 40 klinik. Misalkan lima SIMRS menghasilkan 5 perubahan
        per tahun. Bebannya 800 jam, atau Rp48 juta di sisi klinik, sehingga selisih tadi tertutup.
  \item Tahap menerima hasil pemeriksaan memerlukan akses status dan hasil sesuai kewenangan. Bukan semua tabel laboratorium
        perlu menjadi API. INT-03 memperlihatkan akibat sebaliknya: vendor Medikara+ dapat membaca 140 tabel, padahal
        kebutuhannya 2 tabel. Penurunan dari kebutuhan menghasilkan dua kemampuan, yaitu membaca jadwal dan mencatat janji
        temu, serta menghapus akses atas 138 tabel, atau sekitar 99 persen.
\end{enumerate}

kolom dibaca dari atas ke bawah: tahap, kapabilitas, lalu kandidat. API-06 tidak punya kolom sendiri karena dipakai pada

Tim tidak menjawab permintaan satu per satu. Setiap permintaan diterjemahkan menjadi kemampuan, lalu diperiksa dengan tiga
uji. Tiga temuan menonjol.
\begin{enumerate}
  \item Permintaan vendor bukan kebutuhan atas tabel, melainkan kemampuan penjadwalan. Menjawabnya apa adanya akan menambah

  \item Permintaan dua asuransi digabung menjadi satu kandidat, API-03. Sembilan format pada INT-05 adalah gejala, sedangkan
        kemampuannya satu, yaitu klaim dan penjaminan.
  \item API-08 lolos uji lintas batas, tetapi gagal uji bukti. Baris itu tetap ditulis supaya tidak hilang dari daftar.
\end{enumerate}

Mengapa verifikasi penjaminan pada skema Bab 2 belum masuk delapan kandidat, padahal bernilai Rp960 juta per tahun? Angka itu
bergantung pada 96.000 pemesanan dan kesediaan asuransi membayar. Kontrak dengan 9 asuransi belum ada, dan pemesanannya
bergantung pada API-01. Tim mencatatnya sebagai kandidat lanjutan beserta pemicu tinjauan.

Keputusan ini punya dua konsekuensi. Pertama, pihak yang meminta menerima jawaban berupa kemampuan, bukan persis yang diminta,
sehingga pemilik perlu menjelaskan alasannya. Kedua, daftar kandidat menjadi artefak C3 yang punya versi, bukan kumpulan surat
permintaan.
\end{kasus}

\section{Batas Domain dan Lapisan API}

Delapan kandidat sudah punya nama. Pertanyaan berikutnya: di mana batas satu API berakhir, dan siapa yang memegang aturannya?

Batas domain mengelompokkan makna dan aturan bisnis yang konsisten. Evans memaknai \textit{bounded context} sebagai batas,
biasanya satu subsistem atau pekerjaan satu tim, tempat sebuah model didefinisikan dan berlaku \cite{c08-evans2015}. Lapisan
sistem, proses, dan pengalaman merupakan cara membedakan jenis tanggung jawab API, bukan kewajiban membangun tiga lapisan
fisik. Pembagian ini populer lewat istilah \textit{API-led connectivity}. API sistem mengakses sistem inti, API proses
membentuk data di dalam atau lintas sistem, dan API pengalaman melayani pemakai akhir pada kanal tertentu
\cite{c08-choudhary2023}. Istilah ini berasal dari sisi vendor, sehingga dipakai sebagai alat berpikir. Bahadur, pada blog
vendor yang sama, menyebut anggapan bahwa ketiga lapisan wajib ada sebagai mitos \cite{c08-bahadur2020}. API yang menembus
banyak domain tanpa pemilik dapat menghasilkan ketergantungan serta otorisasi yang sulit dipahami. Analisis domain rinci
dibahas di IT40713.

Analoginya formulir lintas bagian. Satu formulir yang dipakai banyak bagian memerlukan penanggung jawab. Tanpa itu setiap
bagian mengubahnya menurut kepentingan sendiri, dan formulir terus membengkak.

Dua contoh berangka pada Medikara:
\begin{enumerate}
  \item API pengalaman pada aplikasi pasien dapat menggabungkan informasi jadwal dan lokasi, tetapi keputusan mengunci slot
        tetap dimiliki domain penjadwalan. Bab 5 mencatat 28.000 janji temu per bulan dengan tiga panggilan per pemesanan,
        atau 84.000 panggilan. Bila aturan kunci slot disalin ke Medikara+ dan ke sistem 40 klinik mitra, ada 41 salinan
        aturan. Perubahan aturan pembatalan menjadi 41 pekerjaan. Bila dipegang domain penjadwalan, pekerjaannya satu.
  \item API sistem membungkus kemampuan SIMRS lama. Kontrak luarnya tidak perlu membocorkan nama tabel atau kode vendor. Bab
        4 menghitung bahwa menambah satu tujuan secara langsung berarti 5 sambungan baru, atau Rp225 juta per tahun. Lewat
        lapisan, tambahannya 1 sambungan, atau Rp45 juta. Lapisan bersama berbiaya Rp300 juta per tahun, sehingga baru lebih

\end{enumerate}

\section{Lanskap API}

Portofolio menambah API baru, tetapi API baru itu masuk ke lingkungan yang sudah berjalan. Apa yang perlu dilihat sebelum
menambah?

Lanskap API dapat ditelaah melalui delapan aspek: \textit{variety}, \textit{vocabulary}, \textit{volume}, \textit{velocity},
\textit{vulnerability}, \textit{visibility}, \textit{versioning}, dan \textit{volatility} \cite{medjaoui2021continuous}.
Aspek tersebut membantu menemukan jenis keragaman serta ketidakpastian. Penilaian tidak berhenti pada daftar
\textit{endpoint}. Makna istilah, tingkat perubahan, dan keterlihatan pemakaian sama pentingnya dengan besar trafik.
Amundsen, salah satu penulis buku itu, meringkasnya sebagai delapan tantangan yang muncul ketika lanskap membesar
\cite{c08-amundsen2020}.

Analoginya pengelola kota. Pengelola kota memerlukan peta kepadatan, aturan jalan, dan rencana perubahan selain daftar nama
jalan. Menambah satu jalan baru tanpa melihat peta itu dapat memindahkan kemacetan ke tempat lain.

Dua contoh berangka pada Medikara:
\begin{enumerate}
  \item Misalkan tiga API memakai istilah kunjungan dengan makna berbeda. SIMRS menghitung per pendaftaran, Medikara+ per janji
        temu, dan SATUSEHAT per Encounter. Inventaris mencatat 100.000 kunjungan per bulan pada INT-02, 55.000 kunjungan pada
        INT-01, dan 28.000 janji temu pada INT-03. Tanpa kosakata bersama, ketiga angka tampak seperti ukuran satu hal.
        \textit{Vocabulary} menjadi masalah sebelum pengembang menyepakati struktur pesan.
  \item INT-10 mencatat 12 sambungan ke apotek, tanpa pemilik dan tanpa data volume. Bila suatu hari format ekspornya diganti,
        tidak ada yang tahu apotek mana yang terdampak. \textit{Visibility} dan \textit{versioning} harus diperbaiki sebelum
        ada keputusan membangun atau mempensiunkan. Misalkan penelusuran menyita 2 jam per apotek. Bebannya 24 jam, atau
        Rp1,44 juta, jauh lebih kecil daripada Rp45 juta per tahun untuk satu antarmuka yang belum tentu diperlukan.
\end{enumerate}

\cite{c08-amundsen2020}. Arti harfiah kedua kata itu dapat mengarah sebaliknya. Karena itu tim memeriksa gangguan dan keamanan
bersama-sama, dan tidak perlu berdebat tentang labelnya.

Dua hal pada bahasan ini sering tertukar, yaitu lanskap dan portofolio. Pembagiannya begini. Lanskap adalah seluruh API dan

API yang sudah ada, dan 55 persen bergumul dengan dokumentasi yang tidak konsisten \cite{postman2025}. Pada Medikara, gejala itu
sudah terlihat sebelum API mitra pertama lahir.

\section{Kanvas Produk API}

Tim sudah punya kandidat. Bagaimana menguji sebuah kandidat tanpa membangunnya lebih dahulu?

Kanvas produk API memadatkan pengguna, masalah, tawaran nilai, operasi, dependensi, risiko, ukuran, dan pemilik. Kanvas bersifat
hipotesis yang diuji melalui percakapan serta percobaan. Produk API yang bernilai membutuhkan kemampuan pengguna menyelesaikan
pekerjaan, bukan hanya spesifikasi teknis yang lengkap. Delapan unsur ini disusun bab ini untuk keperluan kuliah, bukan istilah
resmi dari satu standar. Bentuk satu halaman berasal dari \textit{Business Model Canvas} Osterwalder dan Pigneur
\cite{c08-osterwalder2010}. APIOps Cycles menurunkannya menjadi \textit{API Business Model Canvas} dengan sembilan unsur, antara
lain segmen konsumen API, hubungan pengembang, mitra utama, manfaat, dan biaya \cite{c08-apiops-bmc}. Kanvas bab ini menambahkan
risiko, dependensi, dan pemilik, karena ketiganya menjadi sumber keputusan pada kasus Medikara.

Analoginya proposal layanan satu halaman. Proposal satu halaman membantu semua pihak memeriksa apakah masalah dan tawarannya
sesuai. Bila masalahnya tidak dapat ditulis dalam dua kalimat, rapat panjang pun belum tentu menolong.

Dua contoh berangka pada Medikara:
\begin{enumerate}
  \item Kanvas janji temu menargetkan petugas klinik, mengurangi telepon konfirmasi, dan mengukur janji yang terkonfirmasi tanpa
        kerja ulang. Pada 40 klinik dengan 60 kunjungan per hari, ada 2.400 pemesanan per hari. Misalkan 10 persen diikuti
        telepon konfirmasi 3 menit. Bebannya 12 jam per hari, atau 300 jam per bulan pada 25 hari kerja, atau Rp216 juta per
        tahun pada tarif Rp60.000 per jam. Bila angka telepon tidak turun setelah API berjalan, hipotesis kanvas salah, walaupun
        API-nya bekerja sempurna.
  \item Kandidat hasil laboratorium menyebut risiko salah pasien serta pembatasan akses. Risiko itu memengaruhi urutan dan desain,
        bukan sekadar lampiran. INT-06 mengetik ulang 1.100 hasil per bulan, atau 13.200 per tahun. Misalkan 0,5 persen salah
        ketik, sehingga ada 66 hasil keliru per tahun. API menghapus salah ketik itu, tetapi memindahkan risiko ke pencocokan
        pasien. Pada 240 hasil per hari untuk klinik mitra, atau 72.000 per tahun, kesalahan 1 dari 10.000 berarti sekitar 7
        hasil salah sasaran. Karena itu \textit{payload} notifikasi pada Bab 5 tidak memuat isi hasil.
\end{enumerate}

\subsection{Pemilik Produk API}

Pertanyaan kemudian muncul: siapa yang mengisi kolom pemilik? Pemilik produk memutuskan prioritas, menanggung anggaran, dan menerima
akibat keputusannya. Tim teknis menjaga kontrak dan operasi. Medjaoui dkk. memandang API sebagai produk, sehingga pemilik diukur dari
hasil bagi pengguna, bukan dari selesainya proyek \cite{medjaoui2021continuous}. Pada Medikara, kapabilitas dan produk berada pada
tingkat yang berbeda. Direktur Pelayanan memegang kapabilitas CAP-L03 menurut peta IT40513, sedangkan Manajer Layanan Rawat Jalan
memegang produk API-01, karena ia yang merasakan akibat antrean.

Analoginya perbaikan pos ronda. Tukang memperbaiki bangunannya, sedangkan warga lewat ketua RT memutuskan kapan pos dipakai dan
perbaikan mana yang lebih dahulu. Tukang yang baik tetap tidak berhak menentukan jadwal ronda.

Dua contoh berangka pada Medikara:
\begin{enumerate}
  \item Misalkan lima rumah sakit mengajukan 12 perubahan API-01 per triwulan, sedangkan kapasitasnya 6. Tanpa pemilik, perubahan
        dikerjakan menurut siapa yang paling dulu menelepon. Dengan pemilik, 6 perubahan dipilih menurut dampaknya pada janji
        terkonfirmasi, dan 6 lainnya diberi alasan tertulis. Konflik yang tidak selesai dibawa ke Direktur Pelayanan.
  \item Bab 4 memisalkan 18 perubahan aturan asuransi per tahun, dan setiap perubahan menjadi permintaan ke vendor seharga Rp8 juta,
        atau Rp144 juta per tahun. Vendor yang dibayar per perubahan tidak punya alasan untuk mengurangi jumlahnya. Karena itu vendor
        bukan otomatis pemilik produk, walaupun vendor paling paham kodenya.
\end{enumerate}

\section{Prioritisasi Portofolio}

Delapan kandidat sudah tertulis, dan anggaran hanya untuk tiga API. Bagaimana memilihnya tanpa rapat yang berakhir dengan suara
paling keras?

Prioritisasi menggabungkan nilai, usaha, risiko, dependensi, dan kapasitas. Bobot serta skala disepakati sebelum skor diisi. Skor
membantu percakapan tetapi tidak menggantikan kewajiban hukum atau prasyarat teknis. Cooper dkk. mempelajari manajemen portofolio
produk baru pada 205 perusahaan di Amerika Serikat. Kelompok berkinerja terbaik memakai prosedur formal yang konsisten, memakai lebih
dari satu metode, dan menekankan metode strategis. Metode keuangan yang paling populer justru memberi hasil portofolio yang lebih buruk
\cite{c08-cooper1999}. Studi itu tentang produk baru, bukan API, sehingga dipakai sebagai alasan memakai beberapa lensa, bukan sebagai
bukti tentang API.

Analoginya menyusun jadwal renovasi rumah. Jadwal memperhatikan manfaat tiap kamar dan prasyarat instalasi, bukan hanya skor keinginan
penghuni. Dapur yang paling diinginkan tetap menunggu pipa air, walaupun pipa air tidak pernah menjadi keinginan siapa pun.

\begin{pendalaman}[title={Pendalaman Teknis (opsional): Menghitung Skor dan Sisa Kapasitas}]
Listing \ref{lst:ch08-skor} memuat dua fungsi dari skrip penilaian. Fungsi pertama menghitung skor tertimbang. Fungsi kedua mengurangi kapasitas
menurut urutan pengerjaan. Perubahan bobot cukup dilakukan pada konstanta, sehingga uji kepekaan pada Latihan 2 tidak memerlukan rumus baru.

\begin{lstlisting}[style=ch08python, caption={Menghitung skor dan sisa kapasitas, tersedia di \berkas{sources/chapter08/hitung-prioritas-portofolio.py}}, label={lst:ch08-skor}]
def hitung_skor(kandidat, bobot):
  """Menghitung skor tertimbang; skor tidak menggantikan prasyarat."""
  skor_nilai = bobot["nilai"] * int(kandidat["nilai"])
  skor_usaha = bobot["usaha"] * (PENGGESER_SKALA - int(kandidat["usaha"]))
  skor_risiko = bobot["risiko"] * (PENGGESER_SKALA - int(kandidat["risiko"]))
  return round(skor_nilai + skor_usaha + skor_risiko, 1)


def hitung_sisa_kapasitas(daftar_kandidat, urutan_terpilih):
  """Mengurangi kapasitas per pekerjaan; kewajiban memakai jam dahulu."""
  kapasitas = ANGGOTA_TIM * JAM_PER_BULAN * BULAN_PER_TAHUN
  jam_per_id = {
    baris["id"]: int(baris["jam_usaha"]) for baris in daftar_kandidat
  }
  sisa = kapasitas - JAM_KEWAJIBAN
  catatan = [("Kapasitas", kapasitas), ("Sesudah kewajiban", sisa)]
  for id_kandidat in urutan_terpilih:
    sisa -= jam_per_id[id_kandidat]
    catatan.append((f"Sesudah {id_kandidat}", sisa))
  return catatan
\end{lstlisting}

Skrip hanya membaca berkas \textit{Comma-Separated Values} (CSV) lokal dan tidak memanggil server.
\end{pendalaman}

\subsection{Membangun Sendiri, Membeli, atau Memakai API Pihak Lain}

Setiap kandidat terpilih masih menyisakan satu pertanyaan: apakah harus dibangun sendiri? Alternatif membangun, membeli, dan memakai API pihak lain
dibandingkan pada horizon biaya dan kendali yang sama. Membangun sendiri memberi kendali, tetapi organisasi menanggung seluruh perawatan. Membeli
memindahkan sebagian pekerjaan ke pemasok, tetapi menambah keterikatan. Memakai API pihak lain berarti aturan dan perubahan ikut pihak itu. Logika
biaya transaksi Williamson membantu di sini: makin khusus sebuah aset bagi satu hubungan, makin kuat alasan untuk mengelolanya sendiri
\cite{c08-williamson1981}.

Analoginya makan siang kantor. Kantor dapat punya dapur sendiri, berlangganan katering, atau memesan dari restoran terdekat. Dapur sendiri masuk akal
bila menunya khusus dan pegawainya banyak. Untuk makan siang biasa, katering sering sudah cukup, dan restoran menentukan sendiri menu serta jam
bukanya.

Dua contoh berangka pada Medikara:
\begin{enumerate}
  \item INT-08 memakai API bank. Bank memiliki datanya, sehingga membangun sendiri tidak masuk akal. Bab 7 menghitung kerja manual Rp36 juta per tahun,
        sedangkan satu antarmuka Rp45 juta per tahun, atau Rp90 juta bila dua bank memakai spesifikasi berbeda. Dari jam kerja saja, memakai API bank
        masih lebih mahal Rp9 juta per tahun. Keputusan dapat berubah bila portal unduhan dihentikan.
  \item API-06 dibandingkan pada horizon tiga tahun. Membangun: Rp72 juta ditambah 3 kali Rp45 juta, atau Rp207 juta. Misalkan membeli: langganan Rp60 juta
        per tahun dan 400 jam penyambungan, atau Rp204 juta. Selisih Rp3 juta terlalu kecil untuk memutuskan. Penentunya adalah hal lain: layanan identitas
        bukan pembeda Medikara, dan 800 jam terbebas. Sisa kapasitas naik menjadi 1.880 jam, tetapi API-03 tetap tidak muat.
\end{enumerate}

\section{Aktivitas: Portofolio API Target}

\textbf{Tujuan.} Tim menurunkan kandidat API dari tujuan strategis dan kapabilitas organisasi, memprioritaskannya, lalu menghasilkan artefak C3 yang dapat ditelusuri dari
persoalan layanan sampai keputusan tim. Organisasi nyata digunakan dengan izin dan anonimisasi. Medikara menjadi alternatif bila akses tidak tersedia.

\textbf{Pembagian peran.}
\begin{itemize}
  \item Anggota berlatar bisnis, kesehatan, hukum, atau akuntansi menilai nilai bagi pengguna dan mitra, serta memeriksa kewajiban dan batas organisasi.
  \item Anggota berlatar teknis menilai usaha, ketergantungan sistem, dan risiko.
  \item Koordinator mencatat keputusan dan memastikan kedua kelompok menyepakati istilah.
  \item Penelaah menantang asumsi tanpa mengganti bukti dengan pendapat.
\end{itemize}

\textbf{Langkah kerja.}
\begin{enumerate}
  \item Ambil kapabilitas serta perjalanan pengguna dari C1 dan IT40513, lalu ambil baris inventaris dan temuan dari C2.
  \item Daftarkan lima sampai delapan kandidat berikut pengguna dan pemiliknya pada salinan \berkas{sources/chapter08/matriks-prioritas-api.csv}. Isi kanvas versi singkat
        untuk tiap kandidat.
  \item Lewatkan kandidat melalui tiga gerbang pada Gambar \ref{fig:ch08-keputusan}. Tulis kandidat yang keluar beserta alasannya.
  \item Sepakati skala dan bobot penilaian sebelum skor dibuka, lalu periksa dependensi dan batas anggaran.
  \item Gambar matriks nilai dan usaha. Hitung sisa kapasitas menurut urutan pengerjaan.
  \item Isi kanvas lengkap pada salinan \berkas{sources/chapter08/kanvas-produk-api.md} untuk dua atau tiga kandidat prioritas sebagai masukan C3.
  \item Tulis portofolio target: status tiap butir, alasan, pemilik, dan pemicu tinjauan. Mintakan persetujuan pemilik proses, atau pemilik yang diperankan anggota tim.
\end{enumerate}

\textbf{Luaran.} Tim menyerahkan portofolio API target, matriks nilai dan usaha, dua atau tiga kanvas produk API, catatan alternatif yang ditolak, dan tautan bukti.

\textbf{Kaitan dengan capstone.} Luaran ini membuka tonggak C3 Kondisi Target. Satu API prioritas dipakai sebagai bahan kontrak OpenAPI di Bab 9, rancangan manajemen API di
Bab 10, serta alur \textit{onboarding} mitra di Bab 11. ID dan versi artefak dipertahankan saat dipakai bab berikutnya.

\textbf{Berkas pendukung.} Daftar lengkap tersedia pada \berkas{sources/chapter08/README.md}. Templat tidak menggantikan percakapan dengan pemilik proses, dan ketidakpastian dicatat
secara terbuka. Data pribadi pasien atau karyawan tidak boleh dipakai. Data organisasi nyata dipakai dengan izin dan dianonimkan.

\section{Ringkasan}

Strategi API menerjemahkan tujuan platform menjadi kemampuan yang dapat dikonsumsi pihak tertentu. Jumlah API bukan strategi, dan keputusan tidak membuka sebuah kemampuan juga bagian dari strategi.
Bukti empiris mendukung keselarasan API dengan tujuan bisnis, bukan pembukaan seluas mungkin. Strategi platform menjawab siapa bertemu siapa, sedangkan strategi API menjawab kemampuan mana yang dibuka,
untuk siapa, dengan batas apa, dan dalam urutan apa.

\textit{Capability map} menjelaskan kemampuan bisnis, sedangkan \textit{value stream} menjelaskan rangkaian nilai dari sudut pengguna. Kandidat muncul ketika kemampuan perlu dipakai lintas batas. Pada
Medikara, satu API janji temu dengan 5 adaptor lebih mahal Rp45 juta per tahun daripada 5 API per SIMRS, tetapi mengurangi 200 sambungan di sisi klinik menjadi 40. Batas domain mengelompokkan makna dan aturan
bisnis yang konsisten. Lapisan sistem, proses, dan pengalaman membedakan tanggung jawab, bukan kewajiban membangun tiga lapisan fisik.

Lanskap API ditelaah melalui delapan aspek, yaitu \textit{variety}, \textit{vocabulary}, \textit{volume}, \textit{velocity}, \textit{vulnerability}, \textit{visibility}, \textit{versioning}, dan
\textit{volatility}. Lanskap memuat semua yang ada, sedangkan portofolio memuat yang dapat diputuskan. Kanvas produk API memadatkan pengguna, masalah, tawaran nilai, operasi, dependensi, risiko, ukuran, dan pemilik
sebagai hipotesis yang diuji. Pemilik produk memutus prioritas dan menanggung akibatnya, sehingga vendor bukan otomatis pemiliknya.

Prioritisasi menggabungkan nilai, usaha, risiko, dependensi, dan kapasitas. Tiga gerbang mengeluarkan kewajiban, kandidat tanpa pemilik, dan kandidat yang punya alternatif lebih murah. Skor membantu percakapan, tetapi
API-06 dengan skor terendah 2,0 tetap didahulukan karena menjadi prasyarat. Portofolio Medikara memuat satu kewajiban dan tiga API, menyita 6.600 dari 7.680 jam, dan menunda API-03 dengan akibat yang tertulis.

Pesan utama bab ini adalah mempertahankan hubungan antara masalah layanan, pilihan yang dipertimbangkan, dan bukti keputusan. Artefak C3 perlu menyebut pemilik serta pemicu peninjauan. Keputusan yang baik menjelaskan
manfaat yang diharapkan sekaligus akibat yang harus ditanggung organisasi, termasuk masalah yang sengaja belum diselesaikan.

\subsection*{Latihan 1: Menurunkan Kandidat dari Kapabilitas}

\begin{enumerate}

  \item Hitung jumlah sambungan dan biaya pada kedua daftar, dengan satuan biaya yang sama.
  \item Jelaskan informasi vendor yang sengaja disembunyikan oleh daftar kedua.
\end{enumerate}

\subsection*{Latihan 2: Memilih Tiga API}

Misalkan Medikara hanya punya anggaran untuk tiga API tahun depan. Susun kriteria prioritisasi, lalu terapkan pada lima kandidat API. Latihan ini membuktikan bahwa urutan portofolio bergantung pada bobot, prasyarat, dan kapasitas, bukan hanya pada skor.
\begin{enumerate}
  \item Tulis lima kandidat beserta bukti masalahnya.
  \item Sepakati skala dan dua perangkat bobot sebelum menilai.
  \item Nilai manfaat, usaha, dan risiko, lalu hitung skor pada kedua perangkat bobot.
  \item Periksa prasyarat, lalu pilih tiga API dalam batas kapasitas.
\end{enumerate}
