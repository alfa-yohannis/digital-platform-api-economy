\section{Pendahuluan}

Bab 3 ditutup dengan tiga sambungan terlemah di ekosistem Medikara Health. Sebanyak 1.100 pemeriksaan
khusus per bulan dari 3 laboratorium mitra dikirim lewat surel berisi hasil pindaian, lalu diketik
ulang ke Sistem Informasi Manajemen Rumah Sakit (SIMRS). Sebanyak 7.800 klaim per bulan diunggah ke
portal 9 asuransi dengan 9 format, dan 468 klaim ditolak karena format. Sebanyak 36 rekap bulanan bagi
perusahaan klien disusun manual selama empat hari kerja. Ketiganya menjadi calon pertama
\textit{Application Programming Interface} (API) mitra. Pertanyaan kemudian muncul: bila ketiganya
dikerjakan seperti biasa, apa yang terjadi setelah proyeknya selesai?

Permintaan integrasi di Medikara selama ini sering selesai sebagai pekerjaan vendor yang terpisah.
Setelah proyek ditutup, tidak jelas siapa menjawab pertanyaan mitra dan siapa membayar perubahan. Bab
ini memperlakukan API sebagai kemampuan layanan yang dipelihara, sehingga biaya, pengguna, dan mutu
tetap terlihat setelah peluncuran. Bahasannya meliputi nilai ekonomi API, API sebagai produk, audiens
API, biaya tersembunyi integrasi \textit{point-to-point}, model bisnis berbasis API, dan cara
menyusun inventaris. Angka tambahan yang diawali kata ``Misalkan'' adalah asumsi latihan. Kesimpulan
untuk organisasi nyata harus diuji dengan wawancara, dokumen, dan pengukuran yang berizin. Hasil bab
ini menjadi bagian tonggak C2 dalam cetak biru transformasi digital.

Rujukan utama bab ini dipakai untuk membedakan konsep dan membangun alasan keputusan, bukan untuk
menggantikan penilaian konteks organisasi. Konsep API sebagai produk dan tiga audiens API diambil dari
Medjaoui dkk. \cite{medjaoui2021continuous}. Bukti dampak ekonominya diambil dari Benzell dkk.
\cite{benzell2024apis}. Gambaran adopsi di industri diambil dari laporan Postman \cite{postman2025}.

\section{Ekonomi API dan Batas Perusahaan}

Membuka kemampuan lewat API menambah biaya dan risiko. Pertanyaannya, mengapa organisasi tetap
melakukannya? Jawabannya ada pada biaya melintasi batas perusahaan.

Ekonomi API adalah pertukaran nilai yang terjadi ketika kemampuan bisnis dapat dipakai pihak lain
melalui antarmuka yang terkelola. Nilainya dapat berupa pendapatan, biaya koordinasi yang turun, dan
layanan baru. Medjaoui dkk. menggambarkan API sebagai sarana bagi perusahaan untuk membuka bisnisnya
kepada pihak ketiga dan tumbuh melampaui batas kemampuannya sendiri \cite{medjaoui2021continuous}.
Batas itu punya penjelasan klasik. Coase berpendapat perusahaan cenderung membesar sampai biaya
mengatur satu transaksi tambahan di dalam perusahaan sama dengan biaya menjalankannya lewat pasar
\cite{c04-coase1937firm}. API mengubah sisi kedua persamaan itu. Bila bertukar data dengan pihak luar
menjadi murah dan dapat diandalkan, pekerjaan yang dulu harus dikerjakan di dalam menjadi layak
dikerjakan bersama pihak luar. Kaitan antara Coase dan API ini adalah penalaran bab ini, bukan temuan
Coase.

Parker, Van Alstyne, dan Jiang menyebut arah ekstremnya sebagai pembalikan perusahaan. Dalam model
mereka, jumlah pengembang yang terus bertambah membuat perusahaan memilih berinovasi lewat kontrak
terbuka dengan pihak luar daripada integrasi vertikal yang tertutup, sehingga pusat penciptaan nilai
berpindah dari dalam ke luar \cite{parker2017ecosystems}. Rumah sakit tidak akan sepenuhnya terbalik,
karena Bab 1 sudah menegaskan layanan klinis inti tetap dikerjakan di dalam. Yang dapat bergeser
adalah lapisan di sekitarnya.

Analoginya warung makan. Pada awalnya warung membuat sendiri sambal, kerupuk, dan es batu, karena
memesan dari luar merepotkan dan barangnya sering terlambat. Begitu pemasok mengantar tepat waktu
dengan harga yang pasti, warung melepas sebagian pekerjaan itu dan memusatkan tenaga pada masakan
utamanya. Warungnya tidak berubah menjadi pemasok. Yang berubah adalah batas pekerjaannya.

Dua contoh penerapan pada Medikara:
\begin{enumerate}
  \item Misalkan mengetik ulang dan memeriksa satu hasil dari laboratorium mitra butuh 6 menit. Dengan
        1.100 pemeriksaan per bulan, biayanya 110 jam kerja per bulan atau 1.320 jam per tahun.
        Misalkan tarif kerja Rp60.000 per jam, sehingga biaya melintasi batas ini Rp79,2 juta per
        tahun. Angka itu tidak pernah muncul di kontrak dengan laboratorium, tetapi dibayar setiap
        bulan.
  \item Misalkan akses status klaim mengurangi 400 telepon per bulan. Dengan 6 menit per telepon, waktu
        kerja yang dapat dialihkan mencapai 40 jam per bulan, atau Rp28,8 juta per tahun. Tidak ada
        uang masuk dari API itu. Nilainya berupa biaya koordinasi yang turun.
\end{enumerate}

data pasien tetap di bawah kendalinya. Yang berubah adalah cara melintasinya.

Dua hal pada ekonomi API sering tertukar, yaitu volume dan nilai. Pembagiannya begini. Volume adalah
banyaknya panggilan. Nilai adalah hasil yang diterima pengguna. Sebanyak 28.000 janji temu per bulan
dengan tiga panggilan per pemesanan menghasilkan 84.000 panggilan. Misalkan panggilan naik menjadi
168.000 per bulan, sedangkan janji temu tetap 28.000. Panggilan per janji temu naik dari tiga menjadi
enam. Kenaikan itu lebih mungkin berasal dari pengulangan akibat \textit{error} daripada dari
pertumbuhan nilai, dan penyebabnya harus diperiksa.

\subsection*{Membaca temuan riset dan laporan industri}

Bukti empiris datang dari Benzell, Hersh, dan Van Alstyne \cite{benzell2024apis}. Perusahaan
tercatat di bursa yang mengadopsi API publik tumbuh tambahan 38,7 persen selama 16 tahun dibandingkan
perusahaan serupa yang tidak mengadopsinya. Penggunaan API murni untuk produktivitas internal tidak
menunjukkan efek yang signifikan. Perusahaan yang menarik lebih banyak pelengkap pihak ketiga tumbuh
lebih cepat. Analisis variabel instrumental mereka mendukung peran sebab akibat API terhadap nilai
pasar. Penelitian yang sama mencatat sisi buruknya, yaitu risiko kebocoran data yang naik. Keterangan
pendanaan artikel itu menyebut dukungan sebagian dari Mulesoft dan Apigee, dua perusahaan di bidang
alat API.

\section{API sebagai Produk}

Dua vendor dapat menyerahkan kode yang sama. Bedanya baru terlihat enam bulan kemudian, ketika mitra
pertama bertanya dan aturan asuransi pertama berubah. Pertanyaannya, apa yang membuat API tetap
berguna setelah serah terima?

Medjaoui dkk. memakai frasa API sebagai produk untuk sudut pandang bahwa API layak mendapat riset
pengguna, prototipe, dan pengujian, serta pemantauan dan pemeliharaan jangka panjang, sama seperti
produk lain \cite{medjaoui2021continuous}. Ada tiga kewajibannya: mengenal audiens, memahami dan
menyelesaikan masalah terpenting mereka, serta memperhatikan masukan mereka. Proyek integrasi berbeda.
Proyek dibatasi ruang lingkup dan tanggal selesai. Proyek tetap diperlukan untuk membangun produk,
tetapi tanggung jawab produk berlanjut setelah serah terima.

Sebuah produk API punya enam unsur yang saling terkait. Pengguna membawa masalah dan tugas. Produk API
adalah kontrak atas satu kemampuan. Sistem penyedia menyimpan aturan dan data di baliknya. Hasil
bisnisnya berupa layanan yang lebih baik atau efisiensi. Bukti manfaat itu sampai kepada pemilik
produk, yang menetapkan prioritas dan anggaran. Operasi dan dukungan menjaga mutu sepanjang siklus.

Analoginya restoran. Kontraktor membangun dapur, dibayar, lalu pulang. Pemilik restoran masih harus
mengganti menu, menjaga mutu, menjawab keluhan, dan melihat piring mana yang kembali dalam keadaan
penuh. Dapur yang rapi tidak menjamin pelanggan datang lagi.

Dua contoh berangka memperlihatkan akibatnya:
\begin{enumerate}
  \item Misalkan API klaim dibangun dengan biaya Rp250 juta. Sembilan asuransi masing-masing mengubah
        aturan dua kali setahun, sehingga ada 18 perubahan per tahun. Sebagai proyek, setiap perubahan
        menjadi permintaan baru ke vendor seharga Rp8 juta, atau Rp144 juta per tahun tanpa anggaran
        yang disiapkan. Sebagai produk, organisasi menyediakan Rp180 juta per tahun untuk pemilik
        produk, dukungan, dan perubahan. Dalam tiga tahun, proyek menelan Rp682 juta dan produk Rp790
        juta. Di atas kertas, produk lebih mahal Rp108 juta.
  \item Selisih itu dibandingkan dengan hasil yang dipantau. Misalkan pemilik produk menurunkan
        penolakan karena format dari 6 persen menjadi 2 persen. Klaim yang ditolak turun dari 468
        menjadi 156 per bulan. Misalkan memperbaiki satu klaim butuh 15 menit. Penghematannya 78 jam
        per bulan, atau Rp56,16 juta per tahun, atau Rp168,48 juta dalam tiga tahun. Angka itu melampaui
        Rp108 juta. Pada pola proyek, penurunan tersebut tidak punya penanggung jawab.
\end{enumerate}

Siklus hidup memperjelas bedanya. Medjaoui dkk. membagi siklus produk API menjadi lima tahap

produksi. Pada tahap terbitkan (\textit{publish}), API sudah tersedia bagi pengguna. Pada tahap
wujudkan nilai (\textit{realize}), API dipakai dengan cara yang mencapai tujuannya. Pada tahap pelihara
(\textit{maintain}), API masih dipakai, tetapi nilainya mendatar atau menurun. Tahap terakhir adalah
pensiun (\textit{retire}), ketika nilainya tidak lagi sepadan dengan biaya pemeliharaan dan keputusan
mengakhiri API sudah diambil. Gambar \ref{fig:ch04-proyek-produk} menyandingkan siklus itu dengan alur

\subsection*{Pengguna, nilai, dan pemilik}

Tiga pertanyaan menguji apakah sebuah API sudah dikelola sebagai produk.

Pertanyaan pertama: siapa penggunanya, dan tugas apa yang sedang ia selesaikan? Medjaoui dkk. mengutip
teori \textit{Jobs to Be Done} dari Clayton Christensen: orang ``menyewa'' produk untuk membuat kemajuan
dalam keadaan tertentu \cite{medjaoui2021continuous}. Pada API klaim, tugas petugas klaim bukan
``memanggil API''. Tugasnya memastikan klaim diterima pada pengiriman pertama.

Pertanyaan kedua: nilai apa yang dapat diukur? Ukuran seperti jumlah \textit{endpoint} menghitung hasil
kerja tim, bukan manfaat. Ukuran yang berguna menghitung hasil bagi pengguna, misalnya janji temu yang
selesai, klaim yang diterima, dan waktu sampai hasil terbaca dokter. Bagi calon mitra, Medjaoui dkk.
menyebut waktu sampai panggilan pertama yang berhasil (\textit{time to first Hello World}) sebagai
ukuran hambatan masuk \cite{medjaoui2021continuous}.

Pertanyaan ketiga: siapa pemiliknya setelah vendor pergi? Pemilik produk memutuskan prioritas,
menanggung anggaran, dan menerima akibat keputusannya. Misalkan API janji temu dipakai lima klinik.
Pemilik produk mengelola prioritas perubahan dan mengukur janji yang selesai, bukan jumlah
\textit{endpoint}. Jabatan itu tidak harus baru. Pada Medikara, manajer layanan rawat jalan dapat
memegangnya, karena ia yang merasakan akibat antrean.

Apakah API internal juga perlu diperlakukan sebagai produk? Medjaoui dkk. menjawab ya, walaupun tidak
dengan besar investasi yang sama. Sebagian besar pengguna API memang rekan kerja di perusahaan yang
sama. Yang berubah adalah kedalaman pengelolaannya, bukan tiga pertanyaan di atas.

\subsection*{Pendekatan API-first}

Bab 1 mencatat bahwa pendekatan \textit{API-first} dibahas di bab ini. \textit{API-first} berarti kontrak
API dipikirkan sejak awal perancangan kemampuan, bukan ditambahkan setelah aplikasinya jadi. Laporan
Postman menggambarkannya sebagai cara memperlakukan API sebagai produk, bukan proyek \cite{postman2025}.
Laporan itu mencatat 82 persen organisasi responden menerapkannya pada tingkat tertentu, tetapi hanya
25 persen yang sepenuhnya. Jarak itu lebih menarik daripada angka 82 persennya. Banyak organisasi
menyatakan arah yang sama, dan lebih sedikit yang sudah menjalankannya.

Analoginya denah rumah. Pemilik dan arsitek menyepakati letak pintu sebelum tukang mengecor. Memindahkan
pintu di denah butuh penghapus. Memindahkannya setelah tembok berdiri butuh palu dan biaya baru.

Dua contoh penerapan pada Medikara:
\begin{enumerate}
  \item Misalkan nama kolom pada kontrak hasil pemeriksaan keliru. Bila ditemukan saat kontrak ditinjau,
        perbaikannya 2 jam kerja. Bila ditemukan setelah 40 klinik mitra terhubung, tiap klinik butuh
        sekitar 4 jam, sehingga totalnya 160 jam ditambah masa transisi.
  \item Misalkan tim Medikara+ menunggu tim SIMRS selesai selama 10 minggu, lalu bekerja 6 minggu. Jika
        berurutan, totalnya 16 minggu. Bila kontrak disepakati dalam 2 minggu pertama, kedua tim bekerja
        bersamaan dengan jawaban simulasi, sehingga totalnya 12 minggu. Hemat 4 minggu, dengan syarat
        kontrak tidak banyak berubah di tengah jalan.
\end{enumerate}

Dua hal pada pendekatan ini sering tertukar, yaitu \textit{API-first} dan API untuk segalanya.
Pembagiannya begini. \textit{API-first} mengatur urutan berpikir ketika sebuah kemampuan memang akan
dipakai sistem lain. Pendekatan ini tidak mewajibkan semua pertukaran memakai API. Bab 1 sudah
menyatakan unggah berkas bulanan masuk akal untuk rekap yang jarang berubah dan dibaca manusia.

\section{Audiens API: Privat, Mitra, dan Publik}

Satu API klaim, satu API jadwal, dan satu API hasil pemeriksaan tidak melayani orang yang sama. Pertanyaan
kemudian muncul: untuk siapa API ini dibuat, dan apa yang berubah bila audiensnya berubah?

API privat melayani kebutuhan internal, API mitra melayani pihak yang disepakati, dan API publik
dirancang bagi audiens luas. Medjaoui dkk. memakai tiga audiens yang sama, yaitu pengembang
internal, mitra bisnis, dan pengembang pihak ketiga yang bahkan tidak dikenal, masing-masing dengan masalah dan cara berpikirnya
sendiri \cite{medjaoui2021continuous}. Zimmermann dkk. memakai pembagian yang mirip dari sisi
visibilitas: \textit{public API} untuk klien yang jumlahnya tidak terbatas atau tidak diketahui,
\textit{community API} untuk kelompok tertutup yang terdiri dari beberapa badan hukum, dan
\textit{solution-internal API} untuk komponen di dalam satu aplikasi \cite{zimmermann2022patterns}.
Pembagian kedua itu lebih sempit di sisi internal. Bab ini memakai istilah privat, mitra, dan publik.

Analoginya loket rumah sakit. Informasi jam buka ditempel di pintu bagi siapa saja. Daftar pasien yang
dirujuk diberikan kepada klinik perujuk sesuai perjanjian. Catatan kerja antarbagian hanya beredar di
dalam, dan tidak semua pegawai boleh membacanya.

Dua contoh penerapan pada Medikara:
\begin{enumerate}
  \item Pencarian jadwal dokter ditawarkan luas dengan informasi minimum. Tangga keterbukaan Bab 3
        menaruhnya pada Tingkat 0: tanpa akun, dengan batas 1.000 panggilan per hari, dan tanpa data
        pasien. Pendaftaran pasien oleh klinik memerlukan identitas mitra dan pembatasan hak, dengan
        kuota 300 panggilan per hari per klinik. Untuk 40 klinik mitra, kapasitasnya paling banyak
        12.000 panggilan per hari.
  \item API privat antarsistem lima rumah sakit tetap memerlukan otorisasi. Lokasi internal tidak
        menjamin setiap pemanggil berhak membaca rekam medis. Bab 3 memisalkan vendor dapat membaca 140
        tabel SIMRS, padahal kebutuhannya 2 tabel. Sisanya, 138 tabel, adalah risiko yang tidak memberi
        manfaat apa pun, walaupun vendor itu bekerja untuk Medikara.
\end{enumerate}

\section{Integrasi Point-to-Point dan Utang Integrasi}

Bab 1 sudah memperkenalkan integrasi \textit{point-to-point} dan rumus $n(n-1)/2$. Pertanyaan berikutnya
lebih praktis: berapa biaya sambungan yang berjalan, dan bagian mana yang tidak terlihat di anggaran?

Integrasi \textit{point-to-point} menghubungkan sistem secara langsung, dengan cara yang dibuat khusus
untuk pasangan itu. Masalahnya muncul ketika setiap hubungan mempunyai format, kredensial, dan prosedur
perubahan yang berbeda. Rumus $n(n-1)/2$ memberi batas atas pasangan, bukan jumlah sambungan yang
berjalan. Sembilan sistem punya batas 36 pasangan. Gambar lima SIMRS dan empat tujuan pada Bab 1 hanya
memuat 20 sambungan, karena sesama SIMRS dan sesama tujuan tidak tersambung. Anggaran dihitung dari sambungan yang
benar-benar berjalan, yaitu 20, bukan dari batas 36.

Analoginya colokan listrik tambahan di kantor lama. Satu colokan tambahan menyelesaikan masalah hari itu.
Sepuluh tahun kemudian, tidak ada yang berani mencabut satu kabel, karena tidak ada kabel yang diberi
penanda dan satu-satunya teknisi yang hafal sudah pindah. Listriknya masih menyala, tetapi setiap
perbaikan menjadi mahal.

Dua contoh penerapan pada Medikara:
\begin{enumerate}
  \item Bab 1 memisalkan perawatan Rp45 juta per integrasi per tahun, sehingga 10 sambungan ke BPJS
        Kesehatan dan SATUSEHAT menelan Rp450 juta. Misalkan biaya yang sama berlaku untuk sambungan ke
        Medikara+ dan sistem \textit{Enterprise Resource Planning} (ERP) keuangan. Sebanyak 20 sambungan
        menelan Rp900 juta per tahun. Menambah satu tujuan berarti 5 sambungan baru, atau Rp225 juta per
        tahun.
  \item Bab 1 menyebut biaya itu belum termasuk pembaruan spesifikasi. Misalkan BPJS Kesehatan dan
        SATUSEHAT masing-masing memperbarui spesifikasi dua kali setahun, dan satu penerapan berbiaya Rp12
        juta. Empat pembaruan yang diterapkan di lima tempat menjadi 20 pekerjaan, atau Rp240 juta per
        tahun. Lewat satu titik, jumlahnya 4 pekerjaan, atau Rp48 juta.
\end{enumerate}

\section{Model Bisnis Berbasis API}

Setelah biaya terlihat, pertanyaan berikutnya muncul: siapa yang membayar API, dan apakah API harus dijual?

Model bisnis API menjelaskan siapa menerima nilai, siapa menanggung biaya, dan lewat apa organisasi
menangkap nilainya. API dapat mendukung transaksi, memperluas saluran, menjual kemampuan, atau memperkaya
layanan utama. Pilihan model mengikuti siapa menerima nilai dan siapa menanggung biaya. Medjaoui dkk. mencatat
pilihan utamanya sebagai pengorbanan antara pendapatan langsung dan perolehan pengguna
\cite{medjaoui2021continuous}. Bila pengguna memperbesar nilai ekosistem, organisasi dapat menyederhanakan
harga demi adopsi.

Analoginya layanan pengiriman barang. Ongkirnya dapat dibayar pembeli, dibayar penjual, atau disubsidi
dalam harga barang. Paketnya sama, jaraknya sama, tetapi siapa yang merasa diuntungkan berbeda. Toko lalu
memilih cara yang membuat pembeli tetap datang.

Dua hal pada model bisnis sering tertukar, yaitu API yang menjadi produk dan API yang mendukung produk.
Pembagiannya begini. Medjaoui dkk. menempatkan Stripe dan Twilio pada kelompok pertama, karena kemampuan
yang dijual berdiri sendiri, misalnya pembayaran dan pesan singkat. Salesforce dan YouTube ada pada
kelompok kedua, karena API-nya ada untuk mendukung platform yang sudah ada. API kelompok kedua sering gratis,
karena pemakaiannya menaikkan nilai bisnis utamanya \cite{medjaoui2021continuous}. Keduanya tetap
dikelola sebagai produk. Yang berbeda adalah cara menangkap nilainya.

Dua contoh penerapan pada Medikara:
\begin{enumerate}
  \item Pada skema Bab 2, klinik mitra membayar langganan Rp3 juta per bulan. Misalkan API penjadwalan tidak
        dikenai biaya per panggilan karena sudah termasuk langganan. Pada kuota 300 panggilan per hari
        selama 25 hari kerja, atau 7.500 panggilan per bulan, langganan itu setara Rp400 per panggilan.
        Pada kebutuhan 180 panggilan per hari, setaranya sekitar Rp667. Tarif per panggilan justru menghukum klinik saat sistem
        mengulang panggilan akibat \textit{error}, sehingga langganan lebih cocok.
  \item Misalkan API klaim menurunkan penolakan karena format, dengan penghematan Rp56,16 juta per tahun.
        Medikara dapat mempertahankan API itu sebagai investasi operasional tanpa menjualnya ke luar.
        Membebankan tarif kepada asuransi malah dapat menahan adopsi, padahal Medikara yang paling
        diuntungkan. Kemampuan ini berbeda dari verifikasi penjaminan pada Bab 2, yang berbayar
        Rp10.000 per verifikasi, karena manfaat verifikasi penjaminan diterima asuransi.
\end{enumerate}

\subsection*{Sektor pembayaran}

Sektor pembayaran memberi contoh yang jelas dari API yang dijual sebagai produk. Stripe menarik 2,9 persen
ditambah 30 sen dolar per transaksi kartu yang berhasil pada tarif standar Amerika Serikat, tanpa biaya
pendaftaran dan biaya bulanan \cite{stripe-pricing}. Transaksi 100 dolar dikenai 3,20 dolar. Penjual
hanya membayar bila transaksinya berhasil, sehingga harga mengikuti nilai yang diterima.

Di Indonesia, Bank Indonesia menetapkan Standar Nasional Open API Pembayaran (SNAP) untuk industri
pembayaran. Standar ini wajib diterapkan bertahap pada setiap \textit{open API} pembayaran. Cakupannya
standar teknis dan keamanan, standar data, spesifikasi teknis, dan pedoman tata kelola, dengan tujuan
memperkuat konektivitas dan interoperabilitas. Pengelolaannya berpindah ke Asosiasi Sistem Pembayaran
Indonesia (ASPI) sejak 1 September 2023 \cite{snap-bi}. Standar seperti ini menyeragamkan cara
tersambung, sehingga biaya satu sambungan baru menjadi lebih mudah diperkirakan. Bagi Medikara, sambungan ke dua
bank mitra, yang kini menuntut rekonsiliasi manual dua jam per hari, menjadi calon pertama untuk diperiksa.

\subsection*{Sektor kesehatan}

Sektor kesehatan berbeda karena data pasien. Data kesehatan bukan komoditas bebas jual. Setiap pemanfaatan
tetap memerlukan tujuan, dasar pemrosesan, kewenangan akses, dan batas penggunaan yang sesuai
\cite{uu27-2022-pdp}. Karena itu Medikara menjual layanan di sekitar data, bukan datanya.

Dua rujukan luar negeri memberi gambaran arah sektor ini. Proyek \textit{Substitutable Medical Applications
and Reusable Technologies} (SMART) bertujuan agar aplikasi medis ditulis sekali dan berjalan tanpa perubahan
pada berbagai sistem teknologi informasi kesehatan. Proyek ini kemudian memakai standar Health Level Seven
Fast Healthcare Interoperability Resources (HL7 FHIR), yang juga dipakai SATUSEHAT \cite{c04-mandel2016smart, satusehat}. Aturan sertifikasi
Amerika Serikat pada \textit{Code of Federal Regulations} (CFR) memperlihatkan bahwa regulator dapat ikut
menentukan siapa membayar. Pengembang API bersertifikat boleh menarik biaya dari penyedia informasi
kesehatan untuk pengembangan, penyebaran, pemutakhiran, dan biaya tambahan menjalankan API. Dari pengguna API,
biaya hanya boleh ditarik untuk layanan bernilai tambah yang tidak diperlukan untuk membangun perangkat
lunak siap pakai. Biaya lain dilarang \cite{c04-cfr170-404}. Aturan itu tidak berlaku di Indonesia. Gunanya
sebagai pembanding ketika Medikara menyusun harga mitranya.

Kesimpulan bagi Medikara: API mitranya termasuk API yang mendukung produk, bukan API yang dijual sendiri.
Keputusan ini punya dua konsekuensi. Pertama, keberhasilan API dinilai dari layanan yang selesai dan
biaya yang turun, bukan dari pendapatan per panggilan. Kedua, pendapatan Rp2,4 miliar per tahun pada Bab 2
datang dari langganan klinik dan verifikasi asuransi, sehingga API yang gagal melayani klinik mengancam
pendapatan walaupun API itu tidak punya harga.

\section{Menyusun Inventaris Integrasi dan API}

Semua keputusan tadi membutuhkan satu daftar. Laporan Postman mencatat 34 persen responden tidak dapat
menemukan API yang sudah ada, dan 55 persen kesulitan dengan dokumentasi yang tidak konsisten
\cite{postman2025}. Open Worldwide Application Security Project (OWASP) juga memasukkan pengelolaan inventaris
yang buruk ke dalam sepuluh risiko keamanan API 2023 \cite{owasp-api2023}. Pertanyaannya, bagaimana menyusun
daftar yang jujur?

Inventaris menghubungkan sistem asal dan tujuan, data, cara pertukaran, audiens, pemilik, serta dampak
kegagalan. Inventaris mencatat semua integrasi, bukan hanya API, karena surel dan unggah berkas juga integrasi.
Bukti dapat berupa dokumen antarmuka, konfigurasi, kontrak vendor, wawancara, dan catatan insiden. Baris yang
belum diketahui tetap dicatat sebagai ketidakpastian. Inventaris yang jujur lebih berguna daripada daftar
lengkap yang dibangun dari perkiraan.

Analoginya daftar aset rumah untuk keperluan asuransi. Daftar itu memuat lokasi, pemilik, dan kondisi, bukan
hanya nama barang. Barang yang belum jelas surat-suratnya tetap ditulis dengan keterangan ``belum diperiksa''.
Melewatkannya justru membuat kerugian tidak dapat diklaim.

Dua contoh penerapan pada Medikara:
\begin{enumerate}
  \item Misalkan hubungan laboratorium ke SIMRS hanya diketahui dari wawancara. Status bukti ditandai
        ``wawancara'' sampai dokumen atau catatan sistem diperiksa. Angka 1.100 pemeriksaan per bulan tetap
        ditulis, disertai tanda asal angka itu.
  \item Misalkan resep dari SIMRS ke 12 apotek berjalan lewat ekspor berkas, dan tidak ada yang mengaku
        sebagai pemilik. Ada 12 sambungan tanpa pemilik. Temuan itu menjadi risiko operasional walaupun
        antarmukanya belum pernah gagal.
\end{enumerate}

\section{Ringkasan}

Ekonomi API adalah pertukaran nilai yang terjadi ketika kemampuan bisnis dapat dipakai pihak lain lewat antarmuka
yang terkelola. API tidak menghapus batas perusahaan. API menurunkan biaya melintasinya, sehingga pekerjaan yang dulu
harus dikerjakan di dalam menjadi layak dikerjakan bersama pihak luar. Benzell dkk. mencatat tambahan pertumbuhan 38,7
persen selama 16 tahun bagi perusahaan tercatat di bursa yang mengadopsi API publik, sekaligus risiko kebocoran data
yang naik. Angka seperti itu dan laporan industri dibaca bersama penerbit, responden, dan apa yang diukur.

API sebagai produk punya pengguna, masalah yang dilayani, pemilik, ukuran keberhasilan, dan siklus pemeliharaan. API
sebagai proyek berhenti pada serah terima. Pada contoh API klaim, produk lebih mahal Rp108 juta dalam tiga tahun, tetapi
penurunan penolakan dari 6 persen menjadi 2 persen menghemat Rp168,48 juta dan punya penanggung jawab. Pendekatan
\textit{API-first} memindahkan keputusan kontrak ke awal, ketika perubahan masih murah.

API privat melayani kebutuhan internal, API mitra melayani pihak yang disepakati, dan API publik dirancang bagi audiens
luas. Audiens berbeda dari kepekaan data, dan lokasi internal tidak menjamin hak akses. Pada Medikara, jadwal dokter
tampil dalam tiga bentuk, hasil pemeriksaan tidak pernah publik, dan vendor yang membaca 140 tabel padahal butuh 2 tabel
menjadi alasan untuk beralih ke API privat.

Integrasi \textit{point-to-point} murah di awal, tetapi utangnya terus berbunga. Medikara membayar Rp900 juta per tahun
untuk 20 sambungan, ditambah sekitar Rp497 juta biaya tersembunyi yang sudah dapat dihitung. Lapisan bersama baru lebih
murah mulai tiga tujuan pada asumsi bab ini. Model bisnis menjawab siapa membayar. Bagi Medikara, API mitra mendukung
layanan dan tidak dijual sendiri, karena data kesehatan bukan komoditas bebas jual.

Inventaris menyatukan seluruh bahasan itu. Sepuluh baris contoh Medikara mewakili 100 sambungan, dan hanya 10 di antaranya
memakai API milik pihak wajib. Tidak semua baris perlu menjadi API: empat baris menjadi calon produk, sisanya dirapikan,
dipantau, atau ditelusuri. Pesan utama bab ini: API yang tidak punya pemilik akan kembali menjadi proyek berikutnya, dan
organisasi baru dapat memilih dengan jujur setelah tahu sambungan apa saja yang sedang dibayarnya.

\subsection*{Latihan 3: Membedakan Produk dan Proyek}

\begin{enumerate}
